# AirBridge32 技术方案与 Agent 开发任务书

## 1. 项目概述

项目名称：AirBridge32（暂定）

项目目标：开发一个适用于 Windows 11 的轻量级原生 Apple AirDrop 接收程序，使用廉价的外置 USB Wi-Fi 网卡实现 AWDL 无线通信，使 iPhone 能通过系统原生「隔空投送」向 Windows 电脑发送文件。

目前已购买硬件：

- Realtek RTL8821CU USB Wi-Fi 网卡。
- Windows 11 x64 电脑。
- 电脑可通过另一块无线网卡或有线网络正常上网。

核心要求：

1. iPhone 无需安装任何第三方应用。
2. iPhone 使用系统原生 AirDrop 发送文件。
3. Windows 11 能发现并接收 AirDrop 文件。
4. 不依赖 WSL2、Linux 虚拟机或完整 Linux 系统。
5. Windows 后台服务尽量轻量，避免长期占用大量内存。
6. 尽量复用已有开源 AWDL、无线驱动及 AirDrop 协议实现。
7. 优先完成真实文件传输，再进行性能优化。
8. 软件与固件必须区分已经实现、已经测试和仍待验证的功能。

不要预设项目一定能够成功，也不要在没有证据时声称 RTL8821CU 已经兼容完整的原生 AirDrop。

## 2. 当前技术路线

首选研究组合：

- WinAWDL：参考或复用 Windows 原生 AWDL 实现。
- OpenIPC/devourer：研究 RTL8821CU 的底层 USB 无线通信能力。
- RTL8821CU：作为实际无线硬件。
- Windows 原生服务：负责设备管理、协议运行、文件接收和后台常驻。

参考仓库：

1. WinAWDL
   https://github.com/raph559/winawdl

2. OpenIPC/devourer
   https://github.com/OpenIPC/devourer

3. OWL
   https://github.com/seemoo-lab/owl

4. OpenDrop
   https://github.com/seemoo-lab/opendrop

5. SwooshDrop
   https://github.com/AlbinoPriest/swooshdrop

不要因为两个项目使用相似的无线芯片，便认定它们可以直接互相调用。

## 3. 首要任务：源码审计，而不是立即编写代码

请先检查上述仓库的最新源码、README、TODO、Issue、提交记录及构建配置。

重点回答以下问题。

### 3.1 RTL8821CU 硬件确认

- 确认实际购买的网卡是否确实使用 RTL8821CU。
- 获取 Windows 设备管理器或 PowerShell 显示的 USB VID/PID。
- 检查 devourer 源码是否明确支持该芯片及对应 USB 设备 ID。
- 确认该支持是已完成的代码路径、仅有设备枚举记录，还是已经通过实际测试。
- 检查是否存在不同硬件版本、不同 VID/PID 或其他芯片替代的风险。
- 明确所需的 Windows USB 驱动绑定方式。

不要只根据商品标题或外壳型号判断芯片。

### 3.2 devourer 的实际能力

逐项检查 RTL8821CU 对应的实现：

- USB 设备初始化。
- 固件加载。
- 寄存器访问。
- USB Endpoint 与传输队列。
- 原始 802.11 帧接收。
- 自定义无线帧发送。
- 监听模式。
- 信道切换。
- 发送完成状态。
- ACK / BlockAck 相关功能。
- 帧聚合支持。
- Windows 下的 libusb、WinUSB 或其他依赖。
- 设备关闭、异常恢复和资源清理。

必须区分：

A. 芯片硬件理论上具备的能力。

B. devourer 已经实现的能力。

C. 已经在 RTL8821CU 上测试通过的能力。

D. 已经在 Windows 上测试通过的能力。

E. 已经用于真实 AirDrop 的能力。

不能将 A、B 自动视为 E。

### 3.3 WinAWDL 的无线后端

重点检查 WinAWDL 的以下模块：

- `driver/regproxy`
- `upstream/devourer`
- `radio`
- `awdl`
- `airdrop`
- `app`
- `installer`

实际目录名称以最新仓库为准。

回答：

1. WinAWDL 的无线层与 AWDL 协议层之间使用什么接口？
2. 无线层是否直接依赖 RTL8852CE 的 PCIe 寄存器、DMA 或专用初始化代码？
3. 哪些代码可以直接复用？
4. 哪些代码必须替换为 USB 后端？
5. devourer 的 RTL8821CU USB 实现能否满足 WinAWDL 无线层的接口要求？
6. WinAWDL 是否能在不加载 PCIe 专用驱动的情况下运行？
7. 是否需要重写 Radio Adapter、发送队列或接收回调？
8. Windows 驱动签名、管理员权限和设备绑定会带来什么限制？

请使用实际文件路径、函数名称和代码引用支持结论。

如果无法确认某项能力，请明确标记为“待验证”，不要猜测。

## 4. 目标软件架构

目标结构如下：

iPhone
  ↓
原生 AirDrop
  ↓
RTL8821CU USB Wi-Fi 网卡
  ↓
Windows USB 驱动 / libusb
  ↓
devourer USB 无线后端
  ↓
WinAWDL 无线适配层
  ↓
AWDL 邻居发现、同步与 IPv6 通信
  ↓
AirDrop 应用层服务
  ↓
TLS / HTTP 等所需协议
  ↓
Windows 文件保存与通知

以上是目标架构，不代表各层目前已经集成或验证成功。

### 重要原则

尽可能复用已有协议实现。

不要在没有必要时重新实现：

- 整套 AWDL 协议。
- 完整 AirDrop 应用层。
- TLS 与 HTTP 基础设施。
- Windows 文件保存和托盘界面。

优先把问题缩小为：

“如何让 WinAWDL 的无线后端通过 RTL8821CU USB 网卡完成正确的 AWDL 无线帧收发？”

如果现有 WinAWDL 与 devourer 的架构无法直接兼容，请先给出证据和替代设计，再实施改动。

## 5. 无线通信与 AWDL 的技术验证

不能将普通 Wi-Fi 连接成功、Monitor Mode 开启或原始帧注入成功视为 AWDL 已经成功。

必须分阶段验证：

### 阶段 A：无线硬件可控

- Windows 能正确识别 USB 网卡。
- 能通过目标驱动初始化设备。
- 能设置目标无线信道。
- 能接收预期的 802.11 帧。
- 能发送指定的测试帧。
- 能正确读取发送状态和接收信息。

### 阶段 B：AWDL 链路

- 能识别真实 iPhone 发出的相关 AWDL 流量。
- 能处理 AWDL 所需的信道调度。
- 能验证同步和邻居发现流程。
- 能识别并正确处理相关服务发现数据。
- 能建立可靠的双向通信路径。

### 阶段 C：网络层

- 验证 IPv6 地址和邻居关系。
- 验证 AWDL 网络接口的数据路径。
- 验证双向数据包传输。
- 检查丢包、超时、重复包及信道切换问题。

### 阶段 D：AirDrop 应用层

- iPhone 能在系统原生 AirDrop 界面中发现目标设备。
- 能正确处理设备身份和接收确认。
- 能完成所需的 TLS、HTTP 等协议交互。
- 能接收真实文件。
- 文件内容、大小和哈希值正确。
- 能连续接收多个文件。

如果阶段 A 或 B 未通过，不要继续开发 GUI 或进行应用层性能优化。

## 6. USB 驱动与 Windows 资源占用

目标是不使用 WSL2。

需要研究：

- 能否直接使用 libusb / WinUSB 操作 RTL8821CU。
- 是否必须为 USB 网卡替换原有驱动。
- 替换驱动后，网卡能否继续作为普通 Wi-Fi 设备使用。
- 如何避免与 Windows 原生无线驱动发生冲突。
- 是否需要管理员权限。
- 如何处理驱动安装、卸载和设备恢复。
- 是否能够让电脑通过另一块网卡或有线网络继续上网。
- 如何实现轻量级后台常驻。

优先采用单个或少量原生 Windows 进程。

不需要为尚未验证的功能引入复杂的服务框架、数据库或大型 GUI。

资源占用必须通过实际运行测量，不要直接把“原生 Windows”宣传为必然只占用几十 MB 内存。

## 7. 性能目标与瓶颈分析

目标性能：

- 第一目标：稳定完成真实 AirDrop 文件接收。
- 第二目标：测量实际持续传输速度。
- 期望目标：5～10 MB/s。
- 更高速度属于后续优化目标，不是现有能力承诺。

请区分以下指标：

1. 无线 PHY 标称速率。
2. 原始无线帧发送吞吐量。
3. AWDL 网络层吞吐量。
4. AirDrop 文件应用层吞吐量。

不能把前三级的测试数字直接作为文件传输速度。

性能测试至少包含：

- 小文件传输。
- 大文件连续传输。
- 多次连续传输。
- 接收方向测试。
- 丢包、超时与重试情况。
- CPU 使用率。
- 内存占用。
- USB 数据传输效率。

重点分析：

- RTL8821CU 单空间流的限制。
- 2.4GHz 与 5GHz 信道条件。
- AWDL 信道调度和切换开销。
- USB 传输队列和批量传输效率。
- ACK / BlockAck 行为。
- 帧聚合是否能够实际用于目标链路。
- WinAWDL 原有优化是否依赖 RTL8852CE 专有能力。

不要为了追求理论速度而牺牲协议正确性或稳定性。

## 8. 分阶段开发计划

### Phase 0：硬件与源码审计

交付：

- 实际网卡 VID/PID。
- RTL8821CU 设备支持证据。
- devourer Windows 构建可行性。
- WinAWDL 无线后端依赖分析。
- 必须修改的文件清单。
- 许可证与依赖兼容性检查。
- 明确的 Go / No-Go 结论。

本阶段不购买其他网卡。

### Phase 1：独立验证 USB 无线后端

交付：

- 可构建的 devourer Windows 测试程序。
- 设备初始化日志。
- 信道控制测试。
- 无线帧接收测试。
- 无线帧发送测试。
- 测试方法和结果记录。

如果 devourer 在 RTL8821CU 上无法完成必要的原始帧收发，应先定位原因，不要直接进入 AWDL 移植。

### Phase 2：适配 WinAWDL

交付：

- RTL8821CU Radio Adapter。
- 设备初始化和关闭流程。
- 无线帧接收与发送接口。
- 发送状态反馈。
- 信道调度接口。
- 编译与运行说明。

尽可能将 USB 特有逻辑限制在无线后端，不要让 AWDL 和 AirDrop 应用层直接依赖 USB 细节。

### Phase 3：真实 AWDL 测试

交付：

- iPhone 邻居发现日志。
- AWDL 同步测试结果。
- IPv6 双向通信测试。
- 失败场景和日志。
- 已知限制清单。

### Phase 4：完整 AirDrop 接收

交付：

- Windows 原生后台服务。
- iPhone 原生 AirDrop 发现与接收。
- 接收确认。
- 文件保存。
- 多文件传输测试。
- 文件完整性验证。

### Phase 5：性能和产品化

交付：

- 稳态吞吐量报告。
- CPU 与内存测试。
- 驱动安装与卸载流程。
- 开机启动和退出机制。
- 断线恢复。
- 日志与故障排查说明。

## 9. 项目约束

1. 不使用 WSL2 作为最终运行依赖。
2. 不要求 iPhone 安装应用。
3. 不把普通 Wi-Fi Direct、HTTP 上传或局域网文件传输冒充原生 AirDrop。
4. 不把模拟数据演示当成真实文件传输。
5. 不在没有源码证据时宣称 RTL8821CU 已经兼容 WinAWDL。
6. 不因 RTL8852CE 已经成功，就认定 RTL8821CU 也能成功。
7. 不在阶段性测试通过前购买更多无线网卡。
8. 不要未经许可直接复制具有不同许可证的代码。
9. 不要为了实现 USB 访问而破坏用户电脑的正常网络配置。
10. 每项功能都必须记录实现状态、验证方法和测试结果。

所有代码变更应尽量小而可回滚，并保留上游项目的来源信息。

## 10. Agent 的首轮任务

请先执行 Phase 0，不要立即开始大规模编写代码。

请输出一份技术审计报告，包含：

A. RTL8821CU 的确切支持情况，附源码路径。

B. devourer 的 Windows USB 后端能否实际构建和运行。

C. WinAWDL 对 RTL8852CE 的专用依赖清单。

D. 从 PCIe 无线后端迁移到 USB 后端所需修改的文件和接口。

E. 最小可行测试程序的设计。

F. 最可能导致项目失败的三个技术风险。

G. 是否值得继续投入开发，以及判断依据。

H. 如果可行，给出 Phase 1 的具体实施步骤和验收标准。

如果当前环境可以访问 GitHub、构建项目或运行测试，请优先使用真实源码和实际构建结果。不要只提供概念性分析。

如果缺少硬件测试环境，明确区分静态代码审计、成功编译和真实无线硬件测试三种证据。

最终目标不是写出一份看起来完整的方案，而是以最少的开发成本，判断 RTL8821CU 能否成为低成本、轻量级、Windows 原生 AirDrop 接收器的可用无线硬件。
