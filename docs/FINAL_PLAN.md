# 最终方案：AirBridge32 V1（2026-10-27 决定）

目标顺序：**手机端体验稳定 > 传输速度 > 分发便利**。本文是决定，不是选项清单；与既有文档冲突时以本文为准，并在实施后回写 README / PLAN。

## 1. 结论

1. 保留 GPL 边界：`radio`（GPL-2.0）+ `awdld`（GPL-3.0）+ 其余 MIT 进程。**不做单进程**。
2. 删除 Dart/Flutter：它只负责启动与显示，不在数据路径，且把启动、日志、监管都绑在一个 27 MB 的壳上。
3. 删除“外置 Python 便携发行版 + Flutter 监管”的启动方式：Python 接收端保留（已验证 1.05 MB/s），但由我们自己的原生托盘监管进程隐藏拉起。
4. 分发形态改为**单文件自解压 exe**：用户下载一个文件，双击即用，无需安装、无需 Python/Flutter、无需管理员（首次驱动绑定除外）。
5. 速度按“时隙 → ACK/TX 优先级 → USB 帧率 → mDNS 开销”四条实测线推进，不靠换语言或换框架；每条线有判据和停止条件。
6. 稳定性靠看门狗 + 分级自恢复 + 常驻，而不是靠“重启整个程序”。

## 2. 验收指标（V1 发布门槛）

| 维度 | 指标 | 测量方法 |
| --- | --- | --- |
| 手机体验 | 打开隔空投送后 P50 ≤ 2 s、P95 ≤ 5 s 看到 AirBridge32 | 10 次打开，录屏 + receiver 日志时间戳 |
| 手机体验 | 连续 20 次传输零手动干预（不重启、不拔插） | 20 次真实文件，同一会话 |
| 速度 | 20 MB 单文件 P50 ≥ 2.5 MB/s，目标 3.5 MB/s | 真实字节 / `/Upload` 头到结束的墙钟时间，3 次取中位数 |
| 速度 | < 1 MB 小文件端到端 ≤ 2 s | 同上 |
| 稳定性 | 连续 20 次传输无崩溃、无残留进程 | 传输中每 5 s 采样进程表 |
| 稳定性 | radio 假死（提交成功但空中无帧）自动恢复 ≤ 10 s | 注入脚本 + ESP32 见证 |
| 稳定性 | 常驻 24 h，工作集 < 150 MB，无句柄泄漏 | 定时采样 |
| 分发 | 单文件 exe ≤ 30 MB；干净机器解压即用；无外置运行时 | 全新 Windows 11 VM 实测 |
| 分发 | 卸载 = 退出 + 删目录，无残留服务/驱动/注册表 | 干净 VM 验证 |

基线提醒：现有 1.05 MB/s 是 7.7 MB 大文件、系统 Python、mDNS 2 s 公告下的数字；当前便携包 215 KB/s 是 1.16 MB 小文件、embeddable Python、mDNS 0.5 s 公告下的数字。**两者不可直接比较**，V1 第一件事就是用同一张 20 MB 文件重建基线。

## 3. 目标形态

### 3.1 进程与文件

| 进程 | 文件 | 许可证 | 职责 |
| --- | --- | --- | --- |
| 监管 + 托盘 | `AirBridge32.exe` | MIT | 单文件自解压、启动顺序、健康检查、自恢复、通知、日志、退出清理、开机自启（C# / .NET Framework 4.8，Windows 自带运行库） |
| 无线 | `airbridge_radio.exe` | GPL-2.0 | USB/固件/PHY、radio_link TCP 49876 |
| 桥 | `radio_pipe_bridge.exe` | MIT | 命名管道 ↔ radio TCP（V2 可并入其它进程） |
| AWDL | `awdld.exe` | GPL-3.0 | OWL 控制面、原始 IPv6 |
| 用户态网络 | `airbridge_netd.exe` | MIT | lwIP、mDNS、TCP 8771 代理 |
| 接收 | `python\python.exe` + `receiver.py` | MIT | TLS / HTTP / DVZip / 文件落盘 |

用户只看到一个 `AirBridge32.exe`；运行时 6 个进程全部无窗口。

### 3.2 数据路径

```text
iPhone ──AWDL──> RTL8821CU ──USB──> airbridge_radio.exe
                                        │ TCP 49876
                                   radio_pipe_bridge.exe
                                        │ 命名管道
                                      awdld.exe
                                        │ 原始 IPv6（TCP 49877）
                                   airbridge_netd.exe（lwIP）
                                        │ UDP 5353 代理 / TCP 8771
                                   receiver.py
                                        │
                                        └──> %LOCALAPPDATA%\AirBridge32\data\received
```

### 3.3 为什么保留 Python

- Python 端已经实测 1.05 MB/s，且 640 行的分块解析、DVZip、路径穿越、空间预算、断流恢复逻辑都有测试覆盖；
- TLS/zlib/tar 在 Python 里的吞吐远高于 3 MB/s，不是当前瓶颈；
- 用 C++ 重写（约 2 周）会把风险集中到一个未验证的协议实现上，与“更稳定”的目标相反。

去 Python 留作 M3 之后的可选项（见 8.2），不作为 V1 的前置。

## 4. 相对现状的增删

删除：

- `app/`（Flutter 壳）与 Dart 工具链依赖；
- PyInstaller / “embeddable Python 发行版”作为启动器的用法（改为监管进程直接拉起 `python.exe`，不再经过壳）；
- 便携包里未使用的 `cryptography` 以外的多余组件按需裁剪（先测体积再动）。

保留并加固：

- `radio`、`awdld`、`netd`、`receiver.py` 的协议与实现；
- 40 MHz / ch149 作为推荐配置（80 MHz 在当前 devourer 路径不可用）。

新增：

- `AirBridge32.exe`：自解压 + 托盘 + 监管 + 看门狗 + 通知 + 单实例；
- 每进程日志轮转与传输 JSONL；一键诊断包；
- 健康检查与分级自恢复（见 6）；
- 单文件打包脚本与干净机器验收脚本。

## 5. 速度：四条实测线

按嫌疑排序，每条都要先测再改；“改完更快”不算结论，必须同一文件、同一时段、三次中位数。

### E1 时隙与信道序列（最可能）

现象：23:01 那次日志里 iPhone 成为 sync master，`149` 只占 16 个时隙中的 4–7 个；上传期间 joined 帧约 150 帧/s（[airbridge32.log:34](../build/portable/AirBridge32/data/airbridge32.log:34)）。1.05 MB/s 那次约需 700 帧/s，说明当时时隙条件明显更好。

- 测：每秒 joined 帧、149 占空比、awdld 队列深度、peer 通道序列变化时刻；
- 改：确认会话期能否进入同信道序列；调整 `-s`/`-j`；把“peer 切走时暂停发送”做成显式策略；
- 停止条件：若占空比无法改善且帧率不升，转 E2。

### E2 ACK 与 TX 优先级

上传是 iPhone→PC，ACK 由我们发；ACK 延迟会压 iPhone 的拥塞窗口。

- 测：ACK 的排队等待时间分布、重传计数、iPhone 侧速率估算（滑动窗口）；
- 改：ACK 走独立高优先级队列；`tx.retry_limit` 按场景设；减少非必要 action 帧；
- 停止条件：ACK 等待 < 2 ms 仍不升速，转 E3。

### E3 USB 帧率与聚合

3 MB/s 约需 2000 帧/s。8821C 没有接收方向硬件 BlockAck（见 [RADIO_CONTRACT.md](RADIO_CONTRACT.md)），所以单帧开销就是上限。

- 测：URB/s、每次完成的帧数与字节、单帧到应用的延迟；
- 改：增加 RX URB 数量/大小、批量提交、去掉每帧分配；
- 停止条件：USB 侧已无排队仍不升速，说明瓶颈在空口/调度。

### E4 mDNS 与发现开销

- 改：公告改为“启动连发 3 次 + 只在收到查询时回复”，空闲不再每 0.5 s 广播；
- 判据：发现延迟不退化（P50 ≤ 2 s），上传期间 mDNS 帧数 = 0。

## 6. 稳定性设计

- **看门狗**：RX 心跳（5 s 无帧）、FW ready、TX 提交/失败计数、USB 错误码、进程存活、端口占用；
- **恢复阶梯**：重开 RX → 重新 Init（不 reset）→ 完整 USB reset → 重启 radio 进程 → 提示用户拔插；
- **已知假死**：radio 曾出现“提交成功、空中零帧”，需完整 reset；检测方式为连续 N 次传输超时或 TX 统计与 ACK 不符，触发一次自动 reset；
- **单实例**：命名互斥体 + 端口占用检测，避免两个实例抢 USB；
- **电源管理**：关闭该设备的 USB 选择性挂起，避免睡眠后假死；
- **崩溃隔离**：监管进程不进入数据路径；子进程退出按 1 s/5 s/30 s 退避重启，10 分钟内 5 次失败则停止并显示原因；
- **日志**：每进程轮转 5 MB × 3；传输 JSONL（字节数、耗时、SHA-256、失败原因）；导出诊断包前脱敏。

## 7. 分发

- 单文件自解压到 `%LOCALAPPDATA%\AirBridge32\<版本>\`，`data\` 跨版本保留；第二次启动不再解压；
- 自解压 stub 用系统自带 `csc.exe` 编 C#（.NET Framework 4.8 为 Windows 10 1903+/11 内置），stub 只有 7 KB，16 MB 全在载荷；不引入打包器、不需要额外运行时；
- 无管理员权限；唯一需要管理员的是 MI_02 绑 WinUSB（Zadig，一次性），后续可选引导式绑定，但**必须先完成回滚演练**；
- 代码签名暂缺：未签名 exe 会触发 SmartScreen，README 如实说明；
- 许可证义务：随包提供 `radio`（含 devourer）与 `awdld` 的对应源码获取方式；Realtek 固件再分发三选一（取得许可 / 运行时加载 / 只发源码），**发布前必须由用户拍板**；
- 卸载：退出 → 删除版本目录；`data\` 询问是否保留。

### 8.2 明确不做（M3 后再议）

- 用 Dart 重写 AWDL/AirDrop（收益未被证明，成本最高）；
- 合并成单进程（GPL-2.0-only 与 GPL-3.0 不兼容）；
- Wintun 回退路线；
- 80 MHz（devourer 路径已实测不可用）；
- 把 receiver 改写成 C++（仅当 M3 证明 Python 或本地回环是瓶颈）。

## 9. 里程碑与判定

| 里程碑 | 时间 | 判定 |
| --- | --- | --- |
| M1 | 第 1 周末 | 单文件可启动；20 MB 基线 ≥ 1 MB/s（相对现状不劣化）；连续 5 次成功 |
| M2 | 第 2 周末 | ≥ 2 MB/s；连续 10 次零干预；假死自动恢复演练通过 |
| M3 | 第 3 周末 | ≥ 2.5–3.5 MB/s；24 h 常驻；分发包完成；决定是否做 8.2 的收尾项 |

Go/No-Go：

- M2 未达 1.5 MB/s：停止打包工作，先解决 E1/E2；不引入新组件；
- M3 未达 2 MB/s：重新评估 5 GHz 与 80 MHz 的可行性，并考虑换 devourer 分支，而不是继续堆应用层优化。

## 10. 风险

| 风险 | 影响 | 处置 |
| --- | --- | --- |
| Realtek 固件再分发无授权 | 无法合法分发 | 用户决策三选一；在此之前只做内部测试包 |
| iPhone 时隙/行为不可控 | 速度上限不确定 | E1 先测；达不到就按 M3 的 No-Go 分支处理 |
| 未签名 exe 被 SmartScreen/AV 拦 | 分发体验差 | 申请代码签名；文档说明；不上自解压混淆 |
| 单文件自解压首次启动慢 | 首启体验 | 解压后写 marker，二次启动直通；体积控制在 30 MB 内 |
| 驱动绑定失败/回滚未演练 | 用户断网 | 回滚演练列为发布前硬门槛 |
